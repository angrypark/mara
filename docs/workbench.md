# 분석 작업실과 결과 계약

분석 작업실에서 실행을 선택하고, 각 역할의 판단·원래 입력·다른 역할과의 연결·근거·출력을 탐색해요. 실제 보유, 이번 후보 제안, 이전 제안, 각 페르소나의 독립 비중을 구분해 비교해요. `defer`의 비중은 검토 중 후보이며 실행 가능한 확정안이 아니에요.

## 읽기 API

| 경로 | 응답 |
|---|---|
| `GET /api/workbench/{scope}` | 최근 40개 실행의 ID·일자·상태 |
| `GET /api/workbench/{scope}/{run_id}` | `mara.workbench/1.0.0` |
| `GET /api/dialogue/{scope}/{run_id}/{agent_id}` | `mara.dialogue/1.0.0` |
| `GET /api/contracts/{name}` | 이름에 해당하는 JSON Schema |

`scope`는 `portfolio` 또는 `demo`예요. 서버의 scope별 세션이 소유자를 정하며 클라이언트가 owner를 지정하지 못해요. 현재 서비스는 기존 loopback 단일 사용자 접근 경계 안에서 동작해요. 원격 다중 사용자 인증을 제공한다는 뜻은 아니에요. 모든 실행 조회는 해당 세션의 소유권을 검사해요.

Workbench는 `run`, `components`, `edges`, `sources`, `portfolio`, `extensions`를 가진 읽기 투영이에요. 각 컴포넌트에는 안정적인 ID·역할·kind·상태·설명용 blocks·원래 input/output·출력 계약 URI·근거 및 이벤트/가이드/모델 참조가 있어요. 관계는 컴포넌트 ID, 근거는 source ID로 연결해요. 입력이 더 필요한 실행·부분 실패·중단된 실행도 조회할 수 있어요.

`contracts/`의 JSON Schema가 공개 계약이고 서버에서 검증해요. 역할 출력 형식과 비중 합·소유권·참조 일관성은 일반 코드로 추가 검사해요. 허용하지 않는 버전과 알 수 없는 필수 구조를 조용히 해석하지 않아요. 확장 값은 `extensions`에 이름 공간을 두고 추가하며 파괴적 변경에는 새 주 버전을 사용해요. 역할 입력은 실제 실행에 사용된 payload여서 역할별로 달라요.

## 역할별 대화

`POST /api/dialogue/{scope}`는 기존 Host/Origin/CSRF 검증을 사용하고 다음 JSON을 받아요.

```json
{"run_id":"run-id","agent_id":"evidence","request_id":"client-generated-unique-id","message":"이 판단의 가장 약한 근거는 무엇인가요?"}
```

202 응답 후 같은 대화 GET으로 상태와 답변을 조회해요. 메시지는 사용자·실행·역할에 귀속되며 원래 역할 가이드/해시·출력 이벤트·질문 당시 문맥을 저장해요. `request_id` 재전송은 중복 호출을 만들지 않으며 다른 내용으로 재사용하면 거부해요. 스레드별 요청 중복을 막고 전체 동시 요청은 2개, 스레드당 질문은 100개로 제한해요. 재시작 때 진행 중이던 요청은 `interrupted`로 남기고 자동 재전송하지 않아요.

질문은 원래 입력의 수치 검증·개인 제약·보유·이전 판단·지식·동료 의견(그 역할에 원래 제공된 범위), 해당 역할 출력과 최종 제안, 최근 10개 메시지를 사용해요. 근거는 직접 인용과 최근 대화 인용을 우선해 20,000자까지 선택하며 누락 수를 전달해요. 전체 문맥 120,000자·가이드 23,000자 한도를 넘으면 핵심 입력을 조용히 자르지 않고 오류로 알려줘요.

실제 분석 scope는 사용자가 설정한 모델/Codex를 호출해요. demo는 합성 응답임을 표시해요. 답변에는 설명·근거 ID·불확실성·다음 질문을 담고 계약/출처를 검사해요. 저장된 판단 근거를 설명하며 모델의 비공개 내부 사고 과정을 요청하지 않아요. 모델에 주문·설정 변경 도구를 제공하지 않고 답변이 실제 보유·공식 제안·활성 지식을 변경하지 않아요.

## 확장

`contracts/agents.json`이 역할 목록이에요. 새 투자 관점은 고유 ID, `kind: perspective`, 역할·이름·설명·별도 가이드 경로를 추가해요. Engine은 registry의 관점을 독립 호출하고 공통 `agent-perspective` 계약으로 검증해요. 실행 시작 때 registry를 동결하므로 현재 registry에서 삭제해도 과거 실행의 역할은 남아요. 작업실은 컴포넌트/블록을 해석하며 관점별 분기나 고정 인원수 없이 보여줘요. 인쇄 리포트도 기록된 registry와 관점 키에 맞게 열과 카드를 늘려요.

새 업무 모듈은 registry만 추가해서 호출되는 것은 아니에요. 책임에 맞는 Engine 호출·전달 관계·출력 계약·투영 연결을 함께 추가해야 해요. 별도 계약 없이 투자 관점으로 가장하지 않아요.

## 과거와 자료 공백

원본 이벤트는 그대로 보존해요. 이전 계약의 출력은 별도 legacy schema로 읽고 형식이 깨진 출력은 실패 상태와 오류를 표시해요. 과거 `defer`에 `review_now`가 남은 경우 투영에서만 `blocked`로 정규화하며 `extensions.projection_corrections`에 원래 값과 이유를 남겨요.

출력의 `facts`/`evidence_ids`는 해당 실행의 `market.facts[].id`만 인용해요. 보유 조회 원본·개인 답변·프로필의 이벤트 ID는 다른 종류의 출처이며 시장 fact ID 칸에 넣지 않아요. 공통 인용 가이드 v1.1과 `citation_scope`가 이 범위를 각 역할에 전달해요. 변경 이유는 보유 조회 원본 ID를 시장 인용으로 사용해 분석이 중단된 사례예요.

출력 형식·비중 합·근거 ID 검증에 실패하면 해당 역할만 원래 입력과 자신의 직전 출력, `output_feedback`으로 한 번 교정해요. 원본 출력과 `agent_validation`의 rejected/accepted·실패 코드·시도 번호를 각각 보존하고, 두 번째도 실패하면 후속 분석을 중단해요. 공급자 인증·시간초과는 이 교정 대상이 아니에요. 개인 맥락 확인 요청이나 정성 위험 검증의 보류를 통과시키기 위해 재시도하지 않아요.

작업실은 형식과 근거·비중의 의미 검증을 모두 적용해 거부된 결과를 채택한 분석으로 표시하지 않아요. `components[].extensions.output_validation`과 **출력·계약 → 응답 검증·교정 이력**에서 시도별 원본 참조를 확인할 수 있어요. 역할 대화는 교정용 거부 출력 대신 채택된 결과와 검증 상태를 받으며, 거부된 지식 계획은 채택된 회고로 제시하지 않아요. 과거 일반 오류도 원본과 대응 입력을 읽기 전용으로 검증해 역할과 실패 조건을 표시하며 원본을 다시 쓰지는 않아요.

기본 시세 수집 경로의 `market.coverage`는 가치평가·거시·뉴스·ETF 내부·비용·충분한 과거 수익률 자료 공백을 설명해요. 해당 경로에서 위험자산을 새로 편입하거나 기존 위험자산을 현금으로 바꾸는 최종 판단은 보류해요. 단순 가격 자료가 풍부한 투자 근거인 것처럼 표시하지 않아요.

주문 실행은 작업실/대화와 연결하지 않아요. 검토 결과의 구조 통과, 매 실행의 R4 검증, 미래 투자 성과는 서로 다른 평가예요.
