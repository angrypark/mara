# 새 구조와 설계 판단

기준은 workspace의 `works/20261114-mara-concept/index.html` v0.3과 2026-11-14 재구축 요청이에요. 기존 코드·구조 문서는 설계에 사용하지 않았어요. 아래 저장소 구조는 새로 정한 구현 선택이에요.

## 역할과 책임

| 개념 | 책임 주체 | 입력 → 결과 |
|---|---|---|
| R1 개인 맥락 | context agent | 목표·소득·지출·기간·현금·손실 허용 → 공통 제약, 누락 |
| R2 시장 근거 | evidence agent + feed 도구 | 출처·시점 고정 시장 팩, 이전 팩 → 변화, 불확실성 |
| R3 다양한 관점 | Buffett / Marks / Bogle agents | 동일한 기본 근거, 개별 가이드 → 독립 제안·반증 조건 |
| R4 검증 | validation agent + domain.py | 수치 및 개인 제약·근거 → 정량 검사와 정성 반론 |
| R5 종합 | leader agent | 세 관점·검증 → 비중·이유·반대 의견·다음 확인 |
| R6 회고 | reflection agent | 과거 실행·현재 평가 → 투자 결과, 과정 평가, 개선 제안 |
| F1 기억 | memory agent + Knowledge/Store | 회고와 활성 지식 → 버전 있는 추가·통합·수정·비활성화·보관 |
| F2 조율 | Engine | 최초/주간 주기, 역할 입력 경계 → 실행 상태·보고서·다음 일정 |

모델 호출은 역할마다 독립된 요청이에요. 세 관점에는 서로의 **현재 실행** 답을 전달하지 않아요. 이전 관점과 회고는 과거 판단을 검토하는 공통 근거예요. 리더에게만 현재 관점 모두와 검증을 전달해요. 리더 결과를 다시 검증해 정량 또는 정성 부적합이면 `defer`로 보류해요. 보류는 보유 자산 매도나 주문 취소를 실행하는 행위가 아니에요.

모델은 자료 해석과 구조화된 제안을 맡아요. 계산·입력 검증·시점 필터·소유권·저장은 Python 코드가 맡아요. JSON 형식 성공은 금융 판단의 정확성 보장이 아니에요. 라이브 모델과 합성 테스트 모델은 명시적으로 분리하며 같은 사용자의 두 모드를 섞지 않아요.

## 영속 모델

SQLite `users`, `events`, `locks`를 사용해요. events는 owner/kind/effective/recorded/run_id/body/digest를 가져요. 원본을 UPDATE/DELETE하려는 작업은 DB trigger가 차단해요. 소유자·종류·시점 인덱스로 조회해요. 내용 해시를 확인하지만, 이 해시는 관리자 변조까지 막는 전자서명은 아니에요.

| kind | 소유 범위 | 의미 |
|---|---|---|
| profile | 사용자 | 목표·제약·소득·지출·납입·주기 버전 |
| actual | 사용자 | 사용자가 확인한 실제 수량·현금·구성 이유·실제 리밸런싱일 |
| cashflow | 사용자 | 날짜·금액·외부 입출금 중복 방지 reference |
| market | 공통 | 당시 가격·근거·출처·발표/인지/유효 시점 원본 |
| run_started / agent_input / agent_output | 사용자 | 의존 실행·사용 문서·전체 입력·모델 식별·응답 |
| proposal / completed | 사용자 | 제안과 실행 결과, 이전 실행 FK 역할의 ID |
| knowledge | 사용자 또는 공통 관리자 | 안정적 key, version, 상태, 출처 event IDs, 이전 버전 |
| guide | 사용자 | 검토자가 적용한 역할 지침 버전·이유 |
| pruning_audit / anchor_check | 사용자 또는 공통 관리자 | 전체 점검·미해결 모순·필수 맥락 보존 확인 |
| failed / recovery | 사용자 | 실패 유형·재시도와 운영 복구 이력 |

하나의 DB에서 사용자 토큰의 해시로 Session을 얻어요. 읽기·쓰기·지식 출처 확인·내보내기는 해당 사용자로 제한해요. 공통 시장 원본은 모든 사용자에게 읽기 허용해요. 공통 지식에서 개인 근거를 참조하는 것은 차단해요. `create-user`, `market`, `shared-knowledge`, `prune-shared`는 DB를 소유한 **로컬 운영자** 명령이에요. 이 CLI를 원격 사용자에게 그대로 노출하는 서버 구조가 아니에요. DB 파일에 직접 접근하는 OS 관리자는 신뢰 경계 안에 있어요. 원격 서비스로 배포하려면 별도 인증 서버와 관리 API 격리가 필요해요.

기존 wiki 데이터는 그대로 보관하며 자동 해석·이관하지 않아요. 새 DB와 기존 wiki 간 의미를 추측해 합치지 않아요. 수동으로 확인한 값만 새 profile/actual에 입력할 수 있어요.

## 최초와 매주 순환

최초: profile + actual + market → R1/R2 → 독립 R3 → R4 → R5 → 최종 R4 → proposal/completed.

주간: 이전 completed 및 연결된 원본 → 실제 결과 계산 → R6 → F1 변경안·전체 pruning → R1/R2 → 독립 R3 → R4/R5/최종 R4. 따라서 이번 회고의 활성 지식이 **이번 다음 제안**부터 사용돼요. 최초 실행은 과거 성과를 만들지 않아요.

실제 NAV는 수량×기준통화 가격+현금이에요. 성과는 날짜별 외부 입출금을 반영한 Modified Dietz예요. 계획 납입은 수익 계산에 넣지 않아요. 실제 배당·이자·수수료·세금은 최종 확인 현금에 반영하고, 외부 입출금으로 중복 입력하지 않아요. 분할·매매가 있었다면 실제 수량을 갱신해야 해요. 보유를 평가일에 재확인하지 않으면 NAV는 참고 평가만 제공하고 PnL·수익률을 확정하지 않아요. 과거 완료 후 뒤늦은 입출금 입력은 차단하고 별도 조정 작업이 필요함을 알려요.

제안을 보유에 자동 복사하는 경로는 없어요. 실제 변경은 `holdings`로 사용자가 확인해 기록해요. 평가 예정일은 완료일+7일, 리밸런싱 예정일은 마지막 실제 리밸런싱일+설정 주기예요. 주간 검토에서 유지·조정·보류 모두 가능해요. `--force`는 명시적인 조기 평가이며 같은 날짜 완료 결과를 덮어쓰지 않아요.

## 활성 지식과 pruning

- 장기 철학: Git의 persona Markdown과 실행 당시 가이드 스냅샷. 주간 성과로 자동 수정하지 않아요.
- 역할 가이드: 기본 Markdown + 사용자별 검토 버전. `restore-guide`도 새 버전으로 기록해요.
- 공통 시장 지식: 공통 관리자만 관리하고 사용자 출처를 금지해요. 날짜가 지난 시장 사실은 현재 분석에서 제외해요.
- 개인 맥락: 최신 profile/actual은 항상 별도로 전달해요. 지식 pruning 대상이 아니에요.
- 실행 원본·회고: 불변 이벤트로 계속 보관해요. 활성 지식이 가리키는 refs에서 원본으로 돌아갈 수 있어요.
- 활성 지식: add/merge/revise/deactivate/archive/restore 이벤트로 현재 상태를 계산해요. 중복 횟수는 occurrences이며 confidence와 연결하지 않아요. 장기 원칙·희귀 위험은 반증 근거 없이 비활성화·보관하지 않아요.

매주 전체 개인 활성 지식을 6,000자 묶음으로 에이전트가 검토해요. 결정 코드가 전체 집합의 만료·정확한 중복을 검사하고, topic/condition이 겹치는 미해결 집합을 남겨요. 의미상 모순·중복 정리는 모델의 제안과 근거가 있어야 적용하며, 서로 다른 관점을 강제로 합치지 않아요. 공통 집합은 운영자가 `prune-shared`로 정기 점검해요. 원본은 보존하고, 상세 지식을 요약한 뒤 보관할 때도 refs를 유지해요.

역할별 지식은 최대 6,000자, 가이드는 22,000자, 실행 입력은 100,000자예요. 초과 시 조용히 자르지 않고 근거 팩 정리를 요구해요. 목표·제약·현 구성 이유·미해결 위험·다음 확인은 별도 anchors로 항상 전달해요. 활성 DB의 항목 수 자체를 강제로 줄이지 않으며, 역할에 실제 넣는 양을 제한해요. 중요하지만 길이가 커서 선택되지 않은 항목은 원본에 남고 조회 가능해요.

## 실패와 운영

실패한 호출과 이전 단계 결과는 감사 기록에 남고 completed는 발행하지 않아요. 리더 제안과 완료 기록은 한 트랜잭션으로 저장해요. 지식 변경 묶음도 원자적으로 저장해요. 회고와 pruning이 성공한 뒤 이후 분석이 실패하면 그 회고 지식은 남아요. 실패 상태를 확인하고 재실행하면 중복 점검을 다시 거쳐요.

사용자별 실행 잠금으로 중복 동시 실행을 막아요. 강제 종료 후에는 프로세스 종료를 확인한 다음 `recover --reason`으로 해제해요. 자동 잠금 만료로 실행 중인 작업을 중복 수행하지 않아요. SQLite WAL, 파일 권한 0600, export의 배타적 생성, 토큰 비기록을 사용해요. DB 백업은 실행 중 파일 단순 복사 대신 SQLite backup API를 사용해요.

## 이번에 확정하지 않은 것

대화 채널, 특정 모델·프레임워크, 가족 단위 계정 통합, 자동 주문, 수익률에 따른 가중치 자동 조정은 구현 요구로 고정하지 않았어요. 공급자별 시장 API·세금 체계·환율 변환은 특정 서비스를 추정하지 않고 시장 팩 경계로 두었어요. 현재 평가 통화는 사용자 기준통화 하나이고, 해외 자산은 출처가 있는 환율로 환산한 가격 팩을 제공해야 해요.
